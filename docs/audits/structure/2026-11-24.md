# Assist With Moving structure map · 2026-11-24

Mapped at `main` `f578b32` (PR #274 merged, so the shared connector contract and prefixed tool names are included). Read-only: this report is the only change. Companion data: [2026-11-24.json](2026-11-24.json).

## 1. Verdict

The repo is fairly close to easy for a future AI to work in. Its guard rails are good: one local check (`npm run check`) covers lint, both typechecks, bindings, contract drift and unit tests. The MCP docs are tested against the code, and the README map is current. I recommend 17 safe steps in 4 pull requests, about 16 thread-hours in total. None of them changes what a person sees or does. Three things hold it back:

1. **One 10,135-line file is the whole API-key door.** `convex/restApi.ts` holds 33 route families and about 120 parsing and shaping helpers. Some of those helpers have already been copied into the one handler that was split out.
2. **Some rules are written out in more than one place.** The value lists (item statuses, confidences, dispositions and so on) are typed by hand in five places across backend, connector and checks. The "is this a loose movable unit" rule exists twice, word lists included. CSV export is copied into six screens, and photo links are fetched separately in twelve. An agent that fixes one copy leaves the others wrong.
3. **Some names point the wrong way.** `mcpPlanning.ts` is the entire canonical AI door, not "planning". `mcpToolsCanonicalQueue.ts` serves the legacy door. There are two files called `restApi.ts`. The folder `move-pages/` mixes live pages with leftovers behind redirects. One feature can carry three or four names across routes, tables and tools.

The two big screens (`plan-workspace-page.tsx`, 7,217 lines; `load-planner-board.tsx`, 4,657 lines) look the scariest, but neither has changed in 90 days. I propose moving only their pure helpers out now. Split the components when work on those screens resumes.

Of the 32 hand-written files over 1,000 lines, 24 get **leave**, 6 get a **split** and 2 get a **partial move** (one shared list or rule). Two-thirds or more earned "leave", as on the pilot repos.

## 4. Organisation problems: where an agent gets lost

**Misleading folders and names**

- `src/components/move-pages/` holds 9 live page bodies next to 4 leftovers whose routes now redirect (`inventory-page`, `photos-page`, `sell-page` at 851 lines, `spaces-page`). AIR-01 covers those 4 and the panels only they use.
- `src/components/layout-studio/` holds one file. The other 99 components sit flat in `src/components/`. Don't reorganise wholesale: moving 99 files churns imports for no behaviour gain. Add structure only where a split creates it.
- `convex/restApi.ts` (the door) and `convex/lib/restApi.ts` (plumbing plus movable-unit summary) share a name. Step 7 fixes this.
- `convex/mcpPlanning.ts` is the entire canonical door backend. `convex/mcpToolsCanonicalQueue.ts` is imported only by `convex/mcp.ts`, the **legacy** door. Every door's backend file starts with `mcp`. Step 1 signposts them; renaming Convex modules would change function paths, so leave the names.
- Convex references written as `(internal as any).mcpPlanning` (17 in `convex/httpRoutes/mcp.ts`, 5 in `http.ts`, 3 in `shareLinks.ts`) and a hand-typed `internalFunctions` signature block in `restApi.ts` are invisible to TypeScript when something is renamed. These are probably deliberate workarounds for Convex type cycles. Leave them, but say so in the map.

## 5. The plan

For steps that add files under `convex/`, also run `npx convex codegen`: the bindings-freshness check fails otherwise. The resulting `convex/_generated/api.d.ts` diff should **only add modules and remove no function**, which proves no Convex API path moved.
