## P0 — Security & data corruption (fix first)

### 1. HIGH — Cross-household read via `saleListings.getForItem`
**File:** `convex/saleListings.ts:513-539`
`getForItem` authorizes the caller against *their own* `householdId`/`moveId` but never verifies the fetched listing (or its item) belongs to that move/household — it returns another tenant's listing for any foreign `itemId`. Every sibling in the file (`markSold` :561-569, `upsertForItem` :444-452) does the check; this is the one outlier, and it's the exact "pass your own household + a foreign id" pattern previously fixed twice in this codebase.
**Failure:** household-A viewer calls `getForItem` with a household-B `itemId` → B's asking price, sold price, and sale status are disclosed.
**FIX:** In the `getForItem` handler, after finding `listing`, add before returning:
`if (listing.householdId !== args.householdId || listing.moveId !== args.moveId) return null;`
(Return null, don't throw — keeps the item-detail "no listing yet" path working.) No caller changes needed.

### 2. HIGH — `items.archive` missing the move/household ownership guard
**File:** `convex/items.ts:1638-1671`
Unlike its neighbors `markTrashed`/`remove`, `archive` never loads the item or checks it belongs to the caller's move: a user with edit rights on *their own* move can soft-delete an item in **any** household by passing a foreign `itemId`. (Pre-existing, not introduced in this range, but same bug class as #1 — ship together.)
**FIX:** At the top of the handler after auth, add:
`const item = await ctx.db.get(args.itemId); if (!item || item.moveId !== args.moveId || item.householdId !== args.householdId) throw new ConvexError("Item not found for this move.");`
Use `ConvexError` (agent-reachable). Mirror the exact guard used in `markTrashed`.

### 3. ⚡ HIGH — Item save silently promotes estimated weight to "actual" and clobbers confidence fields (PR #112)
**File:** `src/components/item-detail-sheet.tsx:329-330, 679-681, 718-720` (found independently by two reviewers)
Two related bugs in the simplified Measurements UI:
- (a) The single weight field initializes from `item.actualWeightLb ?? item.estimatedWeightLb` and submit **unconditionally** writes the parsed value to `patch.actualWeightLb`. The "I only have an estimate" checkbox changes only `weightConfidence`, never which field the value lands in. So: agent captures an item with `estimatedWeightLb: 40`; Scott opens the sheet to fix a name typo and hits Save → `actualWeightLb: 40` is stored. `src/lib/movable-units.ts:401-403` then labels the guess "actual" everywhere, and every `actualWeightLb ?? estimatedWeightLb` fallback is permanently short-circuited.
- (b) Every save force-overwrites `dimensionsConfidence`/`weightConfidence`/`volumeConfidence` to `"low"` (checkbox on) or `"actual"` (checkbox off), even when the Measurements tab was never opened. `isEstimateConfidence` (:235-239) treats only `low|medium` as estimates, so an agent-recorded `weightConfidence: "high"` (a high-confidence *estimate*) initializes the checkbox unchecked → any save rewrites it to `"actual"`; `medium` degrades to `"low"`. The per-input confidence setters (`updateDimensionInput` etc., :601-628) write state the patch then ignores — dead code masking this.

**FIX (a):** In `handleSubmit`, replace the `parsedActualWeightLb` block (:718-720) with:
```ts
if (parsedActualWeightLb !== undefined) {
  if (weightIsEstimate) { patch.estimatedWeightLb = parsedActualWeightLb; }
  else { patch.actualWeightLb = parsedActualWeightLb; }
}
```
Verify `estimatedWeightLb` still exists on `InventoryItemPatch` in `src/lib/inventory-types.ts` (re-add if the PR #112 diff removed it). Also add `clearActualWeight?: boolean` to the patch type and to `convex/items.ts` `update` (patch builder near :1183: `if (args.clearActualWeight) patch.actualWeightLb = undefined;`), and send `clearActualWeight: true` when `weightIsEstimate && currentItem.actualWeightLb != null` — so checking the estimate box actually demotes a mis-recorded actual weight.
**FIX (b):** Capture the initial checkbox values once from the item (`const initialWeightIsEstimate = ...` etc.) and only include a confidence key in the patch when the user actually changed the checkbox or the value:
`if (weightIsEstimate !== initialWeightIsEstimate || parsedActualWeightLb !== (currentItem.actualWeightLb ?? currentItem.estimatedWeightLb)) patch.weightConfidence = weightIsEstimate ? "low" : "actual";` (mirror for dimensions and volume). Add `"high"` to `isEstimateConfidence` so high-confidence estimates round-trip as estimates. Remove the now-dead confidence setters in the input handlers or keep them solely for ProvenanceCard display.

## P1 — Broken features & agent-facing failures

### 4. HIGH — 90s upload timeout makes large files un-uploadable on slow connections (PR #102 regression)
**File:** `src/lib/photo-upload.ts:300, 357` (`UPLOAD_PUT_TIMEOUT_MS` / `request.timeout`)
XHR `timeout` caps *total* request time, not idle time — any file bigger than link-speed × 90s dies even while making steady progress, and since it's deterministic, all 4 retries fail identically → capture lands "failed". The app allows 25 MB images / 100 MB audio / 500 MB video (:124-144). On a 2 Mbps cellular uplink — the environment PR #102 was tuning for — a 25 MB photo needs ~100s; a 500 MB video needs >90s on anything under ~45 Mbps up. Videos are effectively broken since #102.
**FIX:** Replace the hard timeout with a stall watchdog in `uploadFileWithProgress` (:302): remove `request.timeout = UPLOAD_PUT_TIMEOUT_MS` and the `ontimeout` handler; add
```ts
let stallTimer: ReturnType<typeof setTimeout>;
const armStall = () => { clearTimeout(stallTimer); stallTimer = setTimeout(() => {
  // reject BEFORE abort so the AbortError path doesn't wrongly skip retry
  reject(new Error("Upload timed out. Check your connection."));
  request.abort();
  signal.removeEventListener("abort", abortUpload);
}, UPLOAD_STALL_TIMEOUT_MS); };
```
with `export const UPLOAD_STALL_TIMEOUT_MS = 45_000`. Call `armStall()` right after `request.send(file)` and again inside `request.upload.onprogress`; `clearTimeout(stallTimer)` in `onload`/`onerror`/`onabort` and in `abortUpload`. Note the ordering: `request.abort()` fires `onabort` which rejects with `AbortError` (non-retryable) — reject with the plain timeout `Error` synchronously first (a promise ignores the second reject), or set a `timedOut` flag checked in `onabort`. Update `tests/unit/media-upload-retry.test.ts`.
