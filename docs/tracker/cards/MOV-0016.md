## Why this exists

Moving work happens in bright rooms, outdoors, vehicles, and low-light packing
sessions. A trustworthy shared shell should support both light and dark use
without erasing Moving's distinctive visual identity.

## Current truth

The root layout hard-codes the `dark` class, the toast component explicitly
says the app is hard-locked to dark mode, and the manifest/theme color is dark.
CSS contains light and dark tokens, but no user or system preference path was
found. Public phone/tablet/desktop checks showed a coherent dark UI; they do not
prove a complete light appearance.

**Priority:** Later. **Change class:** product visual-system and preference
change.

## Next safe action

Define a Moving-specific light palette, system/default behavior, persisted user
choice, and no-flash hydration approach. Audit every public and representative
product state before presenting the preference as complete.

## Constraints

- Preserve contrast, evidence-photo legibility, printable packets, QR codes,
  maps/plans, destructive states, and Moving's visual identity.
- Avoid theme flash or server/client hydration mismatch.
- Respect system preference while allowing an explicit user choice.
- Theme/component/config changes require normal safeguards.

## Completion evidence

- Public, auth, queue, inventory, photo, load-plan, settings, admin, error, and
  share views pass contrast and visual review in both appearances.
- System, light, and dark choices persist without hydration errors or flash;
  theme-color metadata follows the active appearance where supported.
- 360/768/1366 screenshots, reduced-motion/200% zoom checks, full CI, and live
  verification pass.
- Print/export artifacts retain intentional colors independent of UI theme.

## Unknown or access limitation

No authenticated light-theme prototype or complete contrast inventory exists.
Current token coverage may be incomplete despite both token sets in CSS.
