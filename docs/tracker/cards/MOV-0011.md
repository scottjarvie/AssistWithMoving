## Why this exists

Household moves mix family members, helpers, movers, companies, public packet
recipients, and chosen AIs. People must be able to see and control exactly who
can view or change each move without confusing an expiring packet link with a
private named collaborator.

## Current truth

Source contains household and move-only memberships, roles, sensitive-field
visibility, participant invitations, queue delegation, API-key scopes, share
links with expiry/revocation/action permissions, and private photo defaults.
There is no verified single account view of current people, AIs, keys, grants,
and public links, and this audit did not test the permission matrix or the
complete owner/organizer, member/partner, move-only helper, chosen-AI and
share-link-recipient scenarios. Moving's action-capable expiring
`/share/<token>` packets are an intentional product difference from the Core's
ordinary Unlisted view model; relabeling them would hide rather than resolve
the difference.

**Priority:** Next. **Change class:** product and verification gap.

## Next safe action

Create a unified access inventory and marked-fixture permission matrix for the
five philosophy roles. Prove invite-partner/shared-plan, move-only helper,
revocation, separately granted AI, and bounded recipient-workflow behavior
before choosing presentation details. Preserve Moving-specific action-capable
shares with explicit labels for scope, allowed actions, audience, and expiry.

## Constraints

- Keep new records Private by default and require explicit sharing.
- Never silently widen household, move, sensitive-field, queue, or AI scope.
- Preserve existing action-capable share semantics until a reviewed migration
  and rollback prove otherwise; do not call them Core Unlisted links.
- Permission/schema/UI work uses normal PR, CI, migration, and deployment.

## Completion evidence

- A matrix covers owner, household member, move-only helper, blocked/revoked
  person, scoped API key/AI, expired link, read-only packet, and action-capable
  packet across sensitive and ordinary fields.
- A partner can join and contribute to one shared move plan without gaining
  another person's private Queue or excluded fields.
- A helper/professional is walled to one named move; revocation blocks later
  access while preserving readable attribution.
- A bounded recipient workflow does not create membership or expose another
  move, household, account, Queue or sensitive field.
- The account UI lists every active access path with actor, scope, actions,
  expiry, last use where available, and a tested revoke path.
- Cross-user and cross-move tests prove default privacy and least privilege;
  share recipients see disclosure text before any allowed action.
- Full CI, migration/rollback checks, normal deploy, marked-account browser
  proof, and independent audit pass.

## Unknown or access limitation

No production memberships, grants, keys, share links, or recipient sessions
were inspected. Existing source foundations are verified; live matrix coverage
and safe revocation behavior remain unknown.
