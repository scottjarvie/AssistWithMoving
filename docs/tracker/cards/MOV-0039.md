## Why this exists

Moving runs two MCP doors. The canonical stateless one at `/mcp`
(`convex/httpRoutes/mcp.ts`) has always re-read a grant on every discovery and
every call — `registerGranted` at `convex/httpRoutes/mcp.ts:502` refuses to
even register a tool whose scope the person has not approved.

The other door did not ask anything at all.

`convex/http.ts:1066`, before this Card:

```ts
const authorizeMcp: McpAuthorizerHandler = (_ctx, args) =>
  args.identity?.subject
    ? { allowed: true }
    : { allowed: false, reason: "Sign in with your Assist With Moving account..." };
```

Any Clerk token that resolved to a subject received **all twenty-nine tools**
registered in `convex/mcp.ts` — reading a whole move, writing inventory,
claiming queue work, archiving belongings, uploading photographs, and adding
participants to a move. With:

- no grant row of any kind, so `/settings/ai` showed nothing to revoke;
- no scope check, so `moving.context.read` and `moving.archive` were
  indistinguishable;
- no activity line, so the boundary could not be seen working because it was
  not working;
- no revocation path short of disabling the person's whole account.

This was not a dormant compatibility path. It is the door people are actually
connected through: `movingmanifest.com/mcp/connect`
(`src/app/mcp/connect/route.ts:21`) proxies to the Convex site at `/mcp/legacy`
(`convex/http.ts`, the route loop at the end of the file), and a live connector
session against this site on 19 August 2026 listed the legacy twenty-nine tool
names, not the canonical fifteen.

## Current truth

**Shipped, merged, and deployed to production.** `1bd6dd7` on `main` (PR #204),
deployed by the Vercel production build for that commit, whose `buildCommand`
in `vercel.json` is `npx convex deploy --cmd 'npm run build'` — so the Convex
functions carrying the fix went live with it.

The gate is `convex/lib/mcpLegacyGrantGate.ts`, deliberately pure so the policy
is testable without a Convex context, wired into the gateway by
`createLegacyGrantGate` in `convex/http.ts`.

**Signing in is still the approval.** Scott's ruling stands: "yep sign in IS the
approval... We can opt into blocking if the user wants later." First contact
runs `aiGrants.touchLegacyConnection` (`convex/aiGrants.ts`), which writes a
real `aiGrants` row carrying `LEGACY_AUTO_GRANT_SCOPES` — context read,
evidence read, work write, queue work — bound to the calling client, expiring
in 30 days, with a consent snapshot and an `approved` activity line. Nobody is
left waiting at a settings page they were never told about. What changed is
that a row now exists to read, revoke, expire and attribute.

**Revocation is final.** A grant already bound to this client — active, expired
or revoked — governs, and no new row is written. Without that, revoking would
be undone by the next request whose access token still worked, and the Revoke
button would be a suggestion.

**Scopes are enforced and nothing implies anything else.** Reading context does
not open private photos; writing does not work the queue; nothing implies
archive. The gate runs on `tools/list` filtering as well as `tools/call`, so an
AI is never shown a capability it would only be refused for, and the refusal
still exists underneath if it calls one anyway. The grant is resolved once per
request and reused across the gateway's per-tool authorize calls.

**Two capability changes, deliberately not silent.** Scott's rule is that no
capability the live connector offers today silently disappears. These two do
change, and were called out in the pull request rather than buried:

1. `archive_item` no longer arrives with the connection. `moving.archive` is the
   destructive verb and is absent from what a sign-in hands over, per the
   connector playbook's raised tier. It is one switch away on `/settings/ai`.
2. `add_move_participant` is refused at any scope. `NEVER_PERMITTED` in
   `convex/lib/aiGrants.ts:120` — shipped product copy, rendered on `/ai` and
   `/settings/ai` — already told people a connected AI may never "Invite,
   remove, or change the access of anyone in your household." The tool let an
   AI invite someone by email and set their role on a move. The code now agrees
   with the copy it was already publishing.

Everything else remains reachable on a sign-in grant.

## Next safe action

None for this Card; it is done. The consolidation that follows it is
`MOV-0040`, which also carries the two follow-ups this fix deliberately left
alone: `add_images` / `attach_photos` sitting under `moving.work.write` for
want of a media-write scope, and the canonical door still telling people
"Signing in proved who they are; it did not decide what you may do"
(`convex/httpRoutes/mcp.ts:480`), which is now the opposite of the ruling and
the opposite of what the legacy door does.

## Constraints

- Ship alone. No consolidation work, no surface rewrites, no scope vocabulary
  changes bundled into a security fix.
- Fail closed. A tool registered in `convex/mcp.ts` without a decision in the
  map is refused, and the build breaks.
- Do not invent a sixth scope inside a security fix.
- Refusals say **reconnect**, never **cannot**, and name the actor who can lift
  them. A client told "cannot" reports a working feature as broken.
- Every refusal string stays plain ASCII. A non-ASCII character in a header
  value is a crash, not a style question.

  written separately rather than one derived by subtracting the other, and
  `decideLegacyGatewayAccess`.
- `convex/aiGrants.ts` — `touchLegacyConnection`, which auto-grants on genuine

  refused without a grant; no scope implying another; the never-permitted tool
  refused at full scope; revoked and expired both saying reconnect with the
  settings URL; every message ASCII; and `legacyGatewayCatalogIsComplete`
  asserting a decision exists for each of the 29 tools `convex/mcp.ts`
  actually registers, so adding a tool without deciding its authority fails
  the build.

  `check:convex-bindings-fresh` OK at 148 modules, build green, and all 107

  genuine challenge for an absent token and for a junk bearer. The handshake
  still works; the gate did not break the door.

## Unknown or access limitation

The grant behaviour itself is proved by unit tests and by inspection, **not**
by a live authenticated call. Verifying that a first connection writes a row,
that revoking it refuses the next call, and that `archive_item` is now absent
until the person turns it on, needs a real OAuth round trip that this lane
could not perform. A live connector attempt against this site during the work
returned 404 from its stored endpoint, so no before/after was captured from a
real client either. The first real reconnection is the test.
