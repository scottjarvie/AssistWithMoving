## Why this exists

The night a household arrives at the new place is the moment a move either
feels handled or feels like a disaster. Everything is in boxes, everyone is
tired, and what matters is whether the kettle, the toothbrushes, the phone
chargers, the pet bowls and one set of bedding are somewhere findable rather
than somewhere in a truck.

Moving already knows how to hold that. `firstNight` is one of the ten planning
default keys in `convex/lib/moveFields.ts`, it has a preset with a label and a
handling in `convex/lib/planningDefaults.ts`, the load planner boards it, the
mover, PCS and employer packets carry it, the inventory filters filter on it,
and `convex/lib/moveQuestions.ts` asks a first-night question that reads it.
The web app has always been able to set it.

What could not set it was the connection. A person could hand their move to
their chosen AI, walk it through every room, have it describe each belonging
accurately — and then find that the one tag that turns a captured inventory
into "these are the things you unpack tonight" was unreachable. Both canonical
OAuth write paths hardcoded `planningDefaultKeys: []` on create
(`convex/mcpPlanning.ts`, `convex/mcpToolsWrite.ts`) and had no field at all on
update. The whole downstream machine existed with nothing able to feed it.

This is a gap in a capability `MOV-0033` already delivered and shipped, not a
new product promise. Nothing here reaches past arrival into utilities, address
changes, or a first-week programme; that scope question is Scott's and is
untouched.

## Current truth

`planningDefaultKeys` is writable through both canonical OAuth write paths, in
source, on branch `claude/moving-first-night`. Two rules make it safe.

**The vocabulary is closed.** `normalizePlanningDefaultKeys` in
`convex/lib/moveFields.ts` is the single gate: it refuses anything outside the
ten keys, deduplicates, and preserves order. The published tool schema builds
its enum from the same array (`convex/httpRoutes/mcp.ts`), so a connected AI
both *sees* the vocabulary in `tools/list` and is refused by name if it invents
one. A silently stored typo would be the worst outcome available — it would
read as a successful tag to the AI and to the person while being invisible to
every filter and packet that was supposed to act on it.

**The write is version-safe, because it replaces rather than merges.** An AI
has to be able to remove a tag it got wrong, so the field replaces the stored
set. That makes a blind write dangerous, so a replace must be informed:
`save_inventory` already refused a correction without a matching
`expectedUpdatedAt`, and `upsert_items` now refuses a tag change carrying no
version token at all. Omitting the field leaves stored tags untouched, so a
partial correction — a room rename, a quantity fix — cannot erase them. An
explicit empty array is a deliberate clear.

`get_item` and `get_move_records` now return the current tags alongside
`updatedAt`, so a single read supplies both the tags being replaced and the
token the write must carry. `expectedUpdatedAt` remains optional for every
other field on `upsert_items`, so no existing client is affected.

The authority model is unchanged. Product permission still lives in the durable
grant, never in the token; `save_inventory` still requires `moving.work.write`,
`upsert_items` still resolves the person through the identity bridge, and no
scope was added, renamed, or advertised anywhere new.

Built and tested; **not merged and not deployed.**

## Constraints

- Stay inside the possessions workflow. This Card does not add a post-arrival
  phase, a utilities checklist, an address-change tracker, or a first-week
  plan; the Project Philosophy scopes Moving "from the first possibility to the
  last loose end" and claims no post-arrival system. Whether one belongs is
  Scott's product decision.
- The key vocabulary is closed and shared. Do not let the tool schema, the
  argument validator, and the presets drift apart; derive them from
  `planningDefaultKeys` rather than retyping the list.
- Replace semantics stay paired with a version token. If the compare-and-set
  requirement is ever relaxed, a concurrent edit by the person becomes silently
  droppable, which is exactly the trust failure the connection cannot afford.
- Product permission stays in the grant. No `moving.*` scope may appear in RFC
  9728 `scopes_supported` or the 401 challenge — see the rule at
  `src/lib/mcp-oauth.ts` and its guard in
  `tests/unit/mcp-endpoint-separation.test.ts`.
