## Why this exists

Moving serves MCP through two doors with two different catalogues, two
different authorization models, and two different sets of promises. A person
connecting their AI gets whichever one their client happened to reach.

**The canonical door.** `/mcp` on the Next host (`src/app/mcp/route.ts`)
proxies to the Convex site's `/mcp`, registered by `registerMcpRoutes` in
`convex/httpRoutes/mcp.ts`. Fifteen tools
(`STATELESS_MOVING_TOOL_NAMES`, `convex/httpRoutes/mcp.ts:38-54`), the
2026-07-28 request model, per-tool scope filtering at registration, and
`operationId` idempotency on the write tools.

**The legacy door.** `/mcp/connect` on the Next host
(`src/app/mcp/connect/route.ts:21`) proxies to the Convex site's `/mcp/legacy`,
which mounts the persisted `convex-mcp-gateway` component over the twenty-nine
tools in `convex/mcp.ts`. Until `MOV-0039` it enforced nothing at all; it now
enforces a grant, but it is still a second catalogue with a second vocabulary.

Two doors is not a transition state anybody chose. It is the residue of the
stateless rewrite landing beside the gateway rather than replacing it, and it
costs the product in three concrete ways: a person's `/settings/ai` activity
list means different things depending on which door was used; the published
`/ai` surfaces cannot honestly describe "the tools" when there are two sets;
and the twenty-nine-tool door is the one people actually reach while the
fifteen-tool door is the one the documentation is written about.

## Current truth

The two catalogues are **not** two namings of one capability set. The legacy
door offers four substantial things the canonical door has no tool for at all.
Converging naively onto the canonical fifteen would silently delete them,
which Scott's rule forbids.

**What the fleet audit got right and wrong about this site.**

Verified wrong, 19 August 2026:

- *"Remove `scopes_supported` from the protected-resource metadata."* This site
  already publishes identity scopes only — `["openid", "profile", "email"]` at
  `convex/httpRoutes/mcp.ts:203`, with product scopes deliberately kept out and
  published as a separate vendor hint (`src/lib/mcp-oauth.ts:39-64`, `:107`).
  Removing the field would have been a regression. This independently confirms
  the correction the Finances lane raised: the harm is publishing *product*
  scope names, not publishing identity ones.
- *"The legacy door is at `/mcp`."* It is at `/mcp/connect`. Apex `POST /mcp`
  answers **401 with no redirect**, reaching the canonical door.
- *"Serve both hostnames identically."* The apex is already correct. The real
  problem is different and worse: **`www.movingmanifest.com` has no TLS
  certificate.** `curl` fails with "no alternative certificate subject name
  matches". This is Vercel domain configuration, not code, and no repository
  change can fix or detect it.

**The rest of the audit list, checked.** Several items were better than the
audit assumed and two are worse.

*Better than assumed.*

- **The truth gate already exists and is strict.**
  `tests/unit/mcp-capabilities.test.ts:749-805` extracts the tool list from
  five published surfaces — `public/ai.txt`, `public/llms.txt`,
  `public/llms-full.txt`, `src/app/(marketing)/ai/page.tsx` and
  `src/app/(marketing)/mcp/guide/page.tsx` — and asserts **exact, ordered**
  equality with `STATELESS_MOVING_TOOL_NAMES`, so an extra name fails as
  loudly as a missing one. It also forbids named AI vendors and the retired
  "eight tools" phrasing. The surfaces are hand-written, but they are not
  unchecked. 31 tests pass.
- **`opId` is already done properly on the canonical door.** All nine write
  tools take a required `operationId` (`convex/httpRoutes/mcp.ts:798` through
  `:1148`); all six read tools correctly do not.
  Replay is fingerprinted by SHA-256 over the canonicalised input with the
  opId removed (`:821`), so a replay with the same id and different content is
  detectable rather than blindly returned, and receipts live in
  `mcpOperations` (`convex/schema.ts:1466-1487`).
- **The suggestions surface is already structurally separate from the Queue.**
  `aiPlanningSuggestions` (`convex/schema.ts:2200-2247`, states `pending` /
  `approved` / `edited` / `rejected`) is a different table that no Queue query
  reads, so exclusion is by construction rather than by a filter that could be
  forgotten. The Queue may reference a suggestion one-directionally
  (`convex/queue.ts:42-57`). This is the closest thing in the fleet to the
  Ideas pattern already working.

*Worse than assumed, and the two most valuable remaining fixes.*

- **The canonical door is the JWT-only one.** The audit said to kill the
  JWT-only path; it is the *canonical* door that has it.
  `verifyOAuth` (`convex/httpRoutes/mcp.ts:256`) uses `jose` exclusively
  with no `/oauth/userinfo` introspection, so an opaque access token cannot
  authenticate there at all. The legacy door is the one that does it correctly
  (`convex/http.ts` `resolveMcpIdentity`: JWT primary, userinfo fallback).
  Convergence must carry the legacy door's fallback onto the canonical door,
  not the reverse. **Still open** — deferred out of the token-outcomes fix
  because userinfo returns a subject and no `azp`, and the client id is what a
  grant binds to for per-connection revocation.
- **~~Every failure collapses to 401, including Clerk being unreachable.~~
  Fixed in PR #205 (`c946616`).** The single `catch` that returned 401 for a
  JWKS-fetch failure now classifies three outcomes: token fault → 401, cannot
  check (unreachable/unconfigured) → 503 with `Retry-After`, via
  `isTokenFault` and `serviceUnavailable` (`convex/httpRoutes/mcp.ts:326-332`).
  Recorded here so no one re-opens it as remaining work.

*Checked and found conformant.*

- **Pre-grant behaviour is correct.** An *unauthenticated* `initialize` gets a
  401 with a genuine challenge, which is what a protected resource owes. An
  *authenticated but ungranted* caller reaches the handler: `handleMcp` reads
  the grant at `convex/httpRoutes/mcp.ts:1290-1293` and falls through with
  `grantedScopes = []`, so `initialize` and `tools/list` are answered and only
  `describe_connection` is registered — deliberately outside the scope
  catalogue (registered at `:613`) so an AI can always ask what it is allowed
  to do.

*Not verifiable from inside the repository.*

- **Protocol dialects.** There is no `PROTOCOL_VERSION` constant and no legacy
  version list anywhere in the repo — grepping for `2025-06-18`, `2025-03-26`
  and `protocolVersion` returns nothing outside `node_modules`. Dispatch is
  delegated wholesale to the SDK by one fixed option,
  `legacy: "stateless"` (`convex/httpRoutes/mcp.ts:1313`). Nothing in this
  repository inspects a method name, so "`initialize` is always legacy" is
  neither implemented nor contradicted here. Whether the SDK does the right
  thing is unproven, and the only instrument that settles it is a real client.

**Playbook v1.3.0 (§2.2, §2.6).** The pre-grant surface is per-dialect:
legacy answers `initialize` and `ping`; modern 2026-07-28 answers `initialize`,
`server/discover` and `tools/list` and has **no** `ping` (`-32601`, legacy
only); only `tools/call` refuses, with 403 and a challenge; and an empty
pre-grant server must still declare an explicit `tools` capability. None of
that can be asserted here while dialect handling lives inside the SDK, which
makes "own the dialect dispatch rather than delegating it" a prerequisite for
conforming to §2.2 at all.

One contradiction is already visible without further checking: the canonical
door still tells a connected AI *"Signing in proved who they are; it did not
decide what you may do"* (`convex/httpRoutes/mcp.ts:638`, the
`describe_connection` `next` text). That is now the opposite of Scott's ruling
and the opposite of what the legacy door does after `MOV-0039`. A retired claim
is as dangerous as an absent one, and this one is currently shipped.

## Next safe action

Do **not** start by deleting a door. Two things come first because they are
small, and then the capability gaps, because until those are closed there is no
door that can be the survivor.

**First, the cheap correctness fixes.**

0a. Give the canonical door the legacy door's `/oauth/userinfo` fallback and
    three real token outcomes — `rejected` → 401, `unreachable` or
    `unconfigured` → **503** with "the authorization server could not be
    reached, try again shortly." This is contained, it is the difference
    between a transient Clerk outage and an infinite re-authorisation loop,
    and it does not depend on any of the work below.

0b. Gate the two hard-coded `15`s on the public surfaces
    (`public/ai.txt:127`, `public/llms-full.txt:333`). The existing truth gate
    checks the tool *list* and not the *count*.

0c. Fix, or decide to accept, the CRLF hazard. There is no `.gitattributes`
    and `core.autocrlf=true`, so on a Windows checkout
    `tests/unit/mcp-doc-tool-catalog.test.ts` and `npm run tracker:verify`
    both fail on the untouched baseline — the doc parsers split on `\n` and
    then anchor with `$` against lines still ending in `\r`. The content is
    correct and Linux CI passes, so this costs no production correctness; it
    costs every Windows contributor a false alarm on every run. The sibling
    gate is already hardened (`tests/unit/mcp-capabilities.test.ts:683-684`)
    and shows the pattern.

**Then the capability gaps, in order:**

1. Add `save_evidence_media` (upload and attach), the media-write scope it
   needs, and settle whether that scope is auto-granted or raised.
2. Add move creation to the canonical door.
3. Add transport, zones, and the box lifecycle — packing, placement, capacity
   validation, and item→box conversion — as canonical save tools.
4. **Extend `get_move_records` (and `search_move_records`) to a `transport`
   record kind** — confirmed absent, so both the read (`list_transport`) and
   write (`upsert_transport`) sides are new work, not a filter tweak.
5. Reconcile the two queue tables. `list_queue`/`claim_queue`/
   `submit_queue_result` read `ingestionQueueEntries`, a different table from
   the canonical `queueItems`; converging them needs a migration or a durable
   bridge, and Q8 decides whether the AI's *add* path (`capture_to_queue`)
   survives at all.
6. Restore the partial-collapse losses named in the table above before
   retiring a legacy tool: the household→role map, single-call enumeration,
   `get_item`'s photo ids and gated fields, `update_move`'s structured
   locations, and `upsert_spaces`' room archival.
7. Only then point `/mcp/connect` at the canonical handler, keeping the legacy
   tool names as thin aliases for one deprecation window.
8. Retire the gateway component and `convex/mcp.ts` once no client is using the
   old names.

Derive `/ai`, `/ai.txt` and `/llms.txt` from the surviving catalogue with a
truth gate that fails on an extra name as well as a missing one, and add the
retired-claim assertion for the "signing in did not decide" sentence.

## Constraints

- No capability the live connector offers today disappears without being named
  in a pull request and in this Card. The tables above are that record.
- The Queue law is not negotiable: the AI answers Queue items and never adds to
  them. `capture_to_queue` moves to the suggestions surface or it does not
  survive.
- Do not build the first-week continuity programme. `personal-ai-success-
  scenarios.md` records it as an approved **Later** programme, explicitly not to
  be folded into the current release. First *night* is the current clause.
- Do not remove identity scopes from `scopes_supported`, and specifically do
  not remove `offline_access` if it is ever added — that would cost clients
  their refresh token.
- One catalogue, one derived count. No tool count written as an English word
  anywhere.

Not started. `MOV-0039` is the security half and is done and deployed; this

## Unknown or access limitation

Four things this lane could not settle and that need Scott or the coordinator:

- **`capture_to_queue`.** Removing an AI's ability to add capture notes to the
  Queue is a real workflow change on the site whose capture pipeline is the
  product. Needs Scott's ruling before it moves.
- **The media-write scope tier.** The connector playbook puts attaching a
  photograph in the raised tier because it lands permanently and spends stored
  bytes. That would mean an AI cannot upload a photo until the person turns it
  on — on a site where photographing a room is the main workflow. This is a
  product call, not an engineering one.
- **`www.movingmanifest.com` has no certificate.** Vercel dashboard work.
  Nobody in the repository can do it or detect it from inside.
- **Whether any client is still using the legacy tool names.** Determines the
  length of the deprecation window, and can only be answered from production
  logs.
