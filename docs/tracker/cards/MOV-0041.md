## Why this exists

Every MCP tool handler took the caller's identity as an ordinary argument — a
`caller` object carrying `subject`, a Clerk user id string — and resolved the
person from it with `requireUserBySubject`. None of them consult `ctx.auth`,
and they cannot: `ctx.auth` is null across the gateway component boundary,
which is the entire reason the argument exists. `convex/mcpTools.ts:1-5` says
so in a comment.

That design is sound only while nothing outside the deployment can supply the
argument. Thirty-one of these handlers were exported as **public** Convex
functions — `query`, `mutation`, `action`:

| Module | Public functions |
|---|---|
| `convex/mcpTools.ts` | 6 |
| `convex/mcpToolsWrite.ts` | 8 |
| `convex/mcpToolsImages.ts` | 5 |
| `convex/mcpToolsQueue.ts` | 3 |
| `convex/mcpToolsSetup.ts` | 9 |

A public Convex function is callable by anyone holding the deployment URL, and
that URL is not a secret: it ships to every browser as
`NEXT_PUBLIC_CONVEX_URL`. So the caller did not need a token, an OAuth flow, a
grant, or an account of their own. They needed a Clerk user id and a POST.
Asserting `{ caller: { subject: "user_..." } }` was the whole authentication
story.

What that walks past is every boundary the product has: OAuth entirely, the
grant row and its scopes, the move scope, `NEVER_PERMITTED`, revocation, and
the activity receipts that let a person see the boundary working. `MOV-0039`
had just finished putting a real grant gate on the legacy door — and this path
did not go through the door at all. It reached `addMoveParticipant`,
`archiveItem`, `upsertItems`, `addImages` and the rest directly.

This was pre-existing and not introduced by `MOV-0039`; that Card closed the
front door while this one was a window beside it.

## Current truth

**Fixed, merged and deployed.** All thirty-one handlers are now
`internalQuery` / `internalMutation` / `internalAction`, reachable only from
inside the deployment, which is what makes the injected `caller` trustworthy
again.

The pattern was already in the repository and simply had not been applied
here: `convex/mcpToolsCanonicalQueue.ts` uses `internalQuery` and
`internalMutation` exclusively, and the canonical stateless door reaches its
handlers through `internal.mcpPlanning`. This Card brings the other five
modules to the same standard.

The gateway supports it directly. `convex-mcp-gateway` types a tool's `fn` as
`FunctionReference<McpToolKind, "internal" | "public", any, any>`
(`dist/shared.d.ts:85`) — internal references were always allowed. The
registry in `convex/mcp.ts` now imports `internal` rather than `api` and
registers all twenty-nine tools through it, and the one cross-door call site
(`convex/httpRoutes/mcp.ts`, `get_evidence_media` reaching
`mcpToolsImages.getImages`) follows.

Nothing outside the deployment referenced these functions. The stdio MCP server
in `mcp-server/` has its own implementations over the REST API and does not
touch them, and no page in `src/` imports them — the web app has its own
functions for the same records.

## Next safe action

None for this Card. The audit's follow-ups on the grant gate itself, and the
corrections to `MOV-0040`'s reconciliation tables, are the next work.

## Constraints

- Ship alone, smallest diff. No consolidation work in a P0.
- Do not weaken any handler's own authorization while moving it. Every
  `requireUserBySubject`, household check and role check is untouched; the
  change is visibility only.
- Do not delete a tool to make the guard pass. The guard asserts the counts.
- The gateway must keep dispatching all twenty-nine tools.

## Unknown or access limitation

The exploit was confirmed by reading the function visibility and the Convex
execution model, **not** by firing an unauthenticated call at the production
deployment. Proving it live would have meant performing the bypass against
Scott's real data, which is not a thing to do to demonstrate a bug that the
source already settles. The post-deploy check is the inverse: that a
now-internal function is refused when called publicly, which is safe to try
because it is expected to fail.

`npm run check:convex-bindings-fresh` reports FAILED on a Windows checkout for
this Card's branch. It is the CRLF artifact recorded in `MOV-0040` step 0c, not
drift: converting the file to LF makes the same check pass with an empty
`git diff`, because the content is identical and only the line endings differ.
