## Why this exists

A person who hits a runtime error needs a recovery path they can actually use.
Sending them to an internal planning service contradicts the repository's
no-Linear operating policy and leaves ordinary users without usable support.

## Current truth

`src/app/error.tsx` says a repeated error “belongs in Linear with the route and
browser details.” The product-scoped error boundary already uses the safer
pattern: retry, return to the move list, and contact support with the displayed
digest. Repository instructions, the tracker Guide, README, and current audit
handoffs correctly make Cards / Work Orders / Guide the durable current-work
truth and Linear optional history only.

**Priority:** Now. **Change class:** product change.

## Next safe action

Through a normal isolated branch, PR, full CI, and deployment, replace the root
error copy with a user-reachable recovery route. Record resulting internal work
in the repo-owned tracker, not Linear, and add a unit lock for the root boundary.

## Constraints

- Do not query, reconnect, or depend on Linear.
- Do not expose stack traces, secrets, or raw provider errors.
- Preserve retry behavior and a short diagnostic code that a user can safely
  share.
- Do not use the state-only publication path for the application or test diff.

## Completion evidence

- Root and product error-boundary tests prove that no user-facing recovery copy
  names Linear or another inaccessible internal system.
- A browser-injected root error proves retry plus one reachable help or support
  path on phone and desktop without exposing raw error details.
- The PR passes full required CI and its exact software commit builds and
  deploys normally; production verification is recorded separately.

## Unknown or access limitation

The public audit did not intentionally trigger a production runtime failure.
The finding is verified in current source, while final live error handling must
be tested with a safe injected fixture or preview deployment.
