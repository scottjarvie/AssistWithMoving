A discovery response, SDK harness, client registration, or token exchange does
not prove that a person can use an actual AI product through a full private move
workflow. Each named client needs its own evidence before public instructions
call it supported.

## Why Scott is needed

Everything inside the repository is done and deployed. The last step is not
software — it is a person signing in to production, approving a grant on a real
consent screen, and letting an AI act inside a real move. That needs a
production identity that does not exist yet, and it is the exact class of action
`MOV-WO-010` reserves for Scott: an account, a production secret, and production
data.

An AI cannot create that identity for you. Creating a production account and
handling a production Clerk secret are both outside what an implementation agent
may do, and both would be irreversible in a way a test fixture is not.

## Smallest decision or action

Answer one question: **may a clearly marked synthetic person exist in production
Assist With Moving for the purpose of this proof, and who creates it?**

## Recommendation

**Create one marked synthetic identity in production yourself, then hand it
over.** Concretely: sign up at `movingmanifest.com` with an address you control
that is obviously synthetic (for example a `+awm-proof` tagged alias), create one
throwaway move with no real belongings in it, and tell the executing AI the
email address and the move name. Keep the password. The AI never needs it for
the parts it can do, and for the parts it cannot — the sign-in and the consent
click — you drive the browser for about five minutes while it directs you.

This is the recommendation because it is the only option that produces the
receipt the Work Order actually asks for without expanding anyone's access: no
production Clerk secret leaves the dashboard, no agent holds a credential, and
the synthetic move is deletable afterward with the existing purge path.

## Alternatives and trade-offs

1. **You create the identity and drive the two person-steps** (recommended).
   Five to ten minutes of your time. Produces a real named-client receipt. No
   secret shared, no agent credential.
2. **Give an agent a production Clerk secret key** so it can mint users and
   testing tokens programmatically. Fastest to automate and the worst trade: a
   production secret in an agent's environment is a standing risk far larger
   than the proof is worth, and it still may not clear the OAuth consent screen.
   Not recommended.
3. **Run the full lifecycle against the development Clerk and Convex pair**
   instead. Safe and fully automatable with the credentials already on the
   machine, but it proves the software, not production — which is what the SDK
   harness already proves. It would not let any client stop being Unknown.
4. **Do nothing for now.** Perfectly defensible. The connection stays Partial,
   which is currently the honest label anyway.

## What each choice changes

Option 1 is the only one that can move a named client from **Unknown** to a
dated receipt, and therefore the only one that can move the connection from
**Partial** toward **Current** in the philosophy ledger, `/ai`, and
`/settings/ai`. Options 3 and 4 leave every public claim exactly as it is today.
Option 2 changes the security posture of the whole project and is not worth it.

## Safe default

Option 4 — do nothing, and leave every Partial and Unknown label standing. The
product is deployed and honest today; nothing is broken by waiting, and no
public surface currently claims a client that has not been proved.

## Consequence of waiting

Nothing degrades and nothing misleads anyone: the software is live, the labels
are accurate, and no named client is claimed. What waiting costs is only the
receipt — Moving keeps a fully built, deployed Bring Your AI connection that no
one has yet watched a real AI product walk end to end, so `MOV-WO-010` cannot
close and no setup page can name a client.
