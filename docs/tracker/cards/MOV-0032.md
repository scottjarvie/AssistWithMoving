## Why this exists

Moving's canonical MCP is useful today, but a reusable Bring Your AI connection
also needs current Streamable HTTP behavior, exact protected-resource discovery,
a trustworthy client identity path, and a safe compatibility story. Client ID
Metadata Documents should lead; Dynamic Client Registration should be only a
fallback for clients that need it.

## Current truth

Production `/mcp` returned the correct OAuth 401 challenge on 2026-08-16, and
its protected-resource document named the exact resource and Clerk authorization
server. Source creates the MCP handler statelessly and exposes eight
workflow-native tools with server-derived identity and move access. Completed
`MOV-WO-006` and `MOV-WO-008` prove an official SDK lifecycle and temporary DCR
client cleanup.

The live authorization-server metadata advertises PKCE, token revocation, and
DCR. It does not advertise or prove a Client ID Metadata Document-first path.
The resource display-name disagreement this Card originally recorded was closed
on `main` by PR `#193`, which points all three `resource_name` emitters at
`product.name`; reverified against `origin/main` `1d0b76d` on 2026-08-16. No
dated real-client matrix proves reconnect, stale-tool recovery, or current
metadata-first interoperability. `/mcp/connect`, `/api/mcp`, and stdio remain
separate compatibility doors with different catalogs.

## Next safe action

Create a dated protocol and client-identity matrix for the exact deployed
`/mcp`: transport/protocol negotiation, protected-resource metadata, resource
indicator, token/client claim shape, Client ID Metadata Document validation,
DCR fallback, redirect binding, registry refresh, reconnect, and cleanup. Fix
only verified gaps and preserve an explicit migration path for existing names
and doors.

## Constraints

- Keep `/mcp` stateless. Durable move work and grants live in Moving, not in an
  MCP session.
- Prefer an HTTPS Client ID Metadata Document under the current MCP/OAuth
  requirements; use DCR only as a documented compatibility fallback.
- Preserve PKCE, exact resource identity, short-lived tokens, refresh
  revocation, and fail-closed metadata/redirect validation.
- Preserve `/mcp`, `/mcp/connect`, `/api/mcp`, and stdio as distinct doors until
  migration evidence supports a change. Never advertise OAuth on `/api/mcp`.
- Do not rename/remove tools or a door before real reconnect and stale-catalog
  recovery proof. Domain-prefixed canonical names need a compatibility plan.
- A successful SDK initialize, registration, or token exchange does not prove a
  named AI product lifecycle.
- Do not change Clerk/provider policy, accounts, secrets, DNS, billing, or
  production data under this planning Card.

## Completion evidence

- A dated matrix names the MCP specification/protocol versions, SDK/client
  versions, Streamable HTTP behavior, discovery metadata, resource handling,
  client-registration method, and Current/Partial/Later/Unknown verdicts.
- A valid Client ID Metadata Document connects without DCR; invalid metadata,
  redirect mismatch, stale digest, wrong resource/client, and replay fail closed.
- A client that genuinely requires DCR uses the fallback without making it the
  default, and the temporary registration can be identified and removed.
- Anonymous challenge, protected-resource metadata, resource name/docs,
  wrong-resource/client, expiry/revocation, and CORS/protocol behavior agree on
  the branded `/mcp` route.
- Existing brief/search/read/evidence/save/replay/correction behavior remains
  green, and reconnect/stale-tool recovery is proved after a deployment.
- Every public/AI document names only the exact door/catalog and client behavior
  that passed.

## Unknown or access limitation

This audit used current source and live anonymous metadata. It did not register
a client, change provider configuration, issue an OAuth token, or exercise a
named client product.

  Client ID Metadata Document-first client identity in
  `convex/lib/mcpClientIdentity.ts`: an HTTPS `client_id` is fetched, required
  to name its own URL, checked for usable and non-downgrading redirect URIs,
  digested, and cached briefly. A `client_id` that claims to be a metadata
  document and fails validation is refused with `invalid_client`, never
  downgraded to the fallback. An opaque provider id is accepted and labelled
  `dynamicClientRegistration`. The registration method and metadata digest are
  bound to the grant and shown to the person, and are never treated as a claim
  about which product is connecting. `/.well-known/oauth-protected-resource/mcp`
  now advertises the five product scopes, `client_id_metadata_document_supported`,
  `productGrantRequired`, the grant-manager URL, and an explicit four-door block
  naming `/mcp`, `/mcp/connect`, `/api/mcp`, and the stdio package as distinct.
  No door was renamed, merged, or removed. Enabling the metadata-document path
  in Clerk is a provider action recorded in
  `docs/planning/moving-bring-your-ai-provider-actions.md`; until it is done the
  advertised preference is honest about being a preference. Real-client
  reconnect and stale-catalog recovery remain unproved.
