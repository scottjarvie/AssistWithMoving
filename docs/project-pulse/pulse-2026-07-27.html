Findings

The sign-in vendor loads on every page — even public docs Needs attention

Every public page (homepage, FAQ, the MCP guide) downloads ~765 KB of third-party JavaScript from Clerk, the sign-in service — including, absurdly, a billing widget on the docs page — plus two blocking calls to Clerk's servers and an analytics beacon. The docs page movingmanifest.com/mcp/guide needs none of it. This is the single biggest speed win available: move sign-in loading to only the pages that sign people in. (Fix plan: work package 1.)

The load-plan page re-reads the whole move on every edit Needs attention

The page subscribes to four live data feeds that between them read your items list three times over, your boxes three times, and box contents once per box. Because feeds re-run when anything changes, one item edit re-reads the move's entire dataset four times. Consolidating to one feed is work packages 2–3 of the fix plan.

Inventory ships every detail of every item to draw 10 rows Needs attention

The inventory list downloads all ~35 fields of every item in the move — private notes, provenance records, research text — then shows 10 compact rows. Slimming the list payload (details stay available on tap) is work package 4.

47 of 199 database indexes are dead weight Needs attention

A database index speeds up one kind of lookup but costs a little on every save. 47 of the 199 defined are never used by any code path — the worst table pays for 14 on every item save while using 6. Removing them is a pure win (work package 5).

One page still builds an invisible duplicate of itself Needs attention

The July 20–21 batch fixed hidden duplicate page content in two places but missed the third: the movable-units page — the heaviest page in the app — still builds both its phone layout and its desktop layout and hides one. Finishing the job at the shared component fixes it everywhere (work package 7).

The CI gate doesn't actually block on failing tests Needs attention

The quality gate from #152 blocks merges on code style, type errors, contract drift, and the build — but the 900+ unit tests run as a separate informational job that cannot block a merge. They passed anyway on the latest check (I verified both jobs), but a failing test currently wouldn't stop anyone. There's a one-click fix in the Decisions tab.

First pulse — what is MovingManifest?

A move-inventory system: every item photographed and cataloged, packed into boxes, planned onto trucks, and exported as documentation packets (insurance claims, movers, employers, military PCS moves). It's a Next.js website on Vercel with a Convex backend and Clerk sign-in — and, distinctively, AI assistants are first-class users: they connect over MCP and can catalog, pack, and plan on your behalf. The project is seven weeks old with 501 commits.

New lessons this period

AI assistants have exactly two doors — and they must never be mixed

movingmanifest.com/mcp is the front door: an assistant signs in with your account (OAuth) — recommended, no key handling. /api/mcp is the side door for headless automation with a scoped mmk_ API key. A client built for one door fails confusingly at the other.

We learned this because July's security work locked both doors separately (#146, #147, #157) — the split is now enforced, not just documented.

Merging to main IS deploying — site and backend together

One pipeline: push to main → Vercel builds the site and deploys the Convex backend in the same step. There is no separate "now deploy the backend" chore, and no drift between the two. The flip side: anything merged is live within minutes, so main must always be shippable.

We learned this because the audit verified live-site text that could only exist after July 17's merge — proving merge and deploy are one motion here.

Git can't see that a squash-merged branch is finished

This repo squash-merges pull requests, so a merged branch's commits never appear in main's history and git reports it "unmerged" forever. Always check the branch against merged PRs before worrying — or deleting the wrong thing.

We learned this because feat/move-398-dep-security looked like unfinished work but is PR #149, merged July 18.

The server is fast — the costs live in the browser and the data layer

Every page's server response measured at 10–25 ms; nothing to fix there. The real costs are what ships to the browser (big JavaScript bundles, the sign-in vendor everywhere) and how much the live data feeds re-read when something changes. That's where all eight fix-plan work packages aim.

We learned this because the July 26 audit measured every route on a production build before reading a line of backend code.

Glossary

Pull request (PR)
A packaged, reviewable batch of changes. "Merging" a PR accepts it into the main code line. Numbers like #156 link to the discussion and exact changes on GitHub.
Squash merge
A merge style that compresses a branch's whole history into one commit on main. Tidy history, but git loses the ability to tell that the original branch was merged.
Branch
A parallel line of work in the code repository. Work happens on a branch, then merges into main, the authoritative line.
Worktree
An extra checked-out folder of the same repository, letting two branches be worked on side-by-side on one machine.
CI (continuous integration)
Robots that automatically check every pull request — code style, type errors, tests, the build — before it can merge. Your gate is GitHub Actions, defined in July (#152).
MCP
Model Context Protocol — the standard plug that lets AI assistants (Claude, ChatGPT, Codex) connect to an app and use its features on a person's behalf.
OAuth
"Sign in with your account" for apps and assistants: the assistant gets permission through your normal login, and no password or key ever gets copy-pasted around.
API key
A long secret string (yours start with mmk_) that lets a program act without a login screen. Powerful, so they're scoped, expire, and can be revoked.
Convex
The backend service holding MovingManifest's live database and server logic. Its signature trick: pages subscribe to data, so the screen updates itself the moment data changes.
Clerk
The third-party service that handles sign-in, accounts, and sessions so the project doesn't store passwords itself.
Database index
A lookup table that makes one kind of query fast, paid for by a little extra work on every save. Great when used; pure cost when defined and never queried.
Third-party JavaScript
Code your pages download from someone else's servers (here: Clerk's). It costs load time on every visit and is outside your control, so it should load only where genuinely needed.
